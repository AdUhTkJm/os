\section{VFS}
\label{sec:vfs}

VFS (\textit{virtual file system}) 顾名思义，就应该用 \cpp{virtual} 函数实现。

某种程度上来说算是个双关，不过倒也不是开玩笑。Linux 里用的是一大堆函数指针，虚函数用的 vtable 也同样是一大堆函数指针，两者不应该有什么区别。好消息是，vtable 是不需要 C++ runtime 的，所以我的确就这么做了。

不过如果想把父类转为子类的话， \cpp{dynamic_cast} 需要 C++ runtime：它需要启用 -frtti。所幸对于单继承而言，我们有绕过它的方法，这正是 LLVM 所做的。具体的介绍请见 \cref{sec:rtti}。当然，用一个额外的 \cpp{void* data} 确实可以解决一切，但是这也太麻烦了。

值得注意的是，我们其实并不需要动态的 down-casting，但它的存在对于调试很有好处。例如，我可以检查 /mnt 处的 inode 是不是 ext2 类型的，来判断 mount 到底出了什么 bug。

因此，我的 inode 基类如下：
\begin{minted}{cpp}
class inode {
  atomic<unsigned> refcnt;
protected:
  atomic<unsigned> lnkcnt;
public:
  virtual ~inode() = default;
  virtual size_t read(size_t offset, void* buf, size_t len, int flags) = 0;
  virtual size_t write(size_t offset, const void* buf, size_t len, int flags) = 0;
  // Other virtual member functions
};
\end{minted}

而每种文件系统的 inode 都会实现对应的 read/write 方法。

可以注意到，我维护了两个数据：refcnt 与 lnkcnt。它们的区别是，refcnt 是这个 inode 被内存中其他结构持有的数量，也就是通常的 shared\_ptr 所维护的那个数；而 lnkcnt 则是其他 inode 连接到它的数量，或者说是文件系统中 inode 的 symlink 数。

同样地，我们有两对函数 drop/ref 以及 unlinked/linked 来更改计数器并且释放资源。

当 refcnt 归零时，只有在这个文件在硬盘上有备份的时候，我们才可以直接在内存中删除它。这是文件系统的属性所决定的，比如 ext2 就认为是有备份的，而 tmpfs 则没有。（我们暂时不会 swap。）如果删除了没有硬盘备份的 inode，之后再想打开的时候，数据就没有了。所以，对这种 inode 而言，只有确认了“无法再次打开”之后才可以删除，而这正是 lnkcnt 所做的事情。

同理，如果 lnkcnt 归零但是有 refcnt，我们也暂时不能删除：可能还有进程在使用它，得等使用完了再删掉。在使用完成后 refcnt 会自然减少，所以不必担心会漏掉。

这样的坏处是，对于 ext2 而言，我们需要维护两份 lnkcnt。一份作为 metadata 写进硬盘，另一份留在内存里，不过只要在创建和删除时注意一下就可以了。ext2 的不少数据也都是这样的。

inode 会持有一个指向它的文件系统的指针： \cpp{class fs *fs}。在内存中的文件系统主要负责分配新的 inode 和回收不用的 inode.对于不在硬盘上的文件系统而言，这就是普通的 new/delete，再加上 refcnt 的管理;对于 ext2 而言，这就不一样了。在\cref{subsec:ext2}中对它有详细描述。

至于文件，则是在 inode 之上再包裹一层：
\begin{minted}{cpp}
class file {
  atomic<unsigned> refcnt;
public:
  inode *node;
  size_t offset;
  int flags;
  enum whence {
    begin, current, end
  };

  void drop();
  void ref() { refcnt++; }

  file(inode *node, int flags);
  ~file();

  size_t read(void *buf, size_t len);
  size_t write(const void *buf, size_t len);
  size_t seek(long pos, whence whence); // Returns the old offset.
  result close();
};
\end{minted}

两者之间的关系是极其显然的。这里 file 析构时，也会调用 \cpp{node->drop()} 来释放 inode。

\section{文件查找}

VFS 本体负责查找一个路径所对应的 inode。它会在每个路径的构成部分都检查一遍 mount point，如果有的话就切换到 mount 的文件系统的根部。这之后，它会调用当前 inode 的 lookup() 虚函数来找到下一个 inode，或者依靠 readlink() 来跟随链接。它也会记录每种文件系统的“构造函数”——虽然不是语法意义上的构造函数，并在 mount 系统调用的时候通过这些函数来创建内存中的文件系统。

VFS 还维护着一个 dcache，将 \cpp{pair<inode *, string>} 映射到 \cpp{dentry*}。这里的 dentry 是一个记载着 inode 和它的名称的结构；inode 本身是没有记录名称的。换句话说，dcache 会记录之前查找过的 inode 对应的目录下的文件，这样再次查找时就无需从头开始了。
