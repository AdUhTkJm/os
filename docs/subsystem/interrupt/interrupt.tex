\section{中断处理}
\label{sec:interrupt}

每个进程都有两个栈：一个是给自己的，一个是给 kernel 的。

在中断的时候，我们想把所有的寄存器都存到 kernel 的栈上，不过我们显然需要一个额外的临时寄存器。RISC-V 提供了一个名为 sscratch 的 CSR，我选择用它保存 user-stack 的位置。这就是 PCB 中的 usp 字段（\cref{sec:pcb}）。

这样我们就腾出了一个 sp 寄存器。我们需要在只有这一个寄存器的情况下找到当前进程 kernel-stack 的位置，也就是 PCB 中的 ksp 字段。在 C++ 中，这是 \cpp{scheduler.active->ksp}，所以只需要访问两次成员变量就可以了，而这确实是可以由一个寄存器完成的。为了防止后续修改影响这个偏移量，我们使用 \cpp{static_assert} 来保证偏移量和汇编中的偏移量能对上。此外，VSCode 的 clangd 插件是可以直接显示 class/struct 中每个字段的偏移量和 padding 的，因此获取这个值也不是难事。

接下来，我们把 31 个寄存器存进 ksp 中，顺便存好几个 CSR，特别是上面提到的 sscratch。（显然寄存器 zero 是无需保存的。）我们还要靠它们返回中断发生的位置。

下面我们就可以调用\cref{sec:interrupthandler}中描述的中断处理器了，这部分来自 C++ 代码。它可能会更改 \cpp{scheduler.active}，所以从中断中返回时还需要重新获取当前进程 ksp 的位置。

最后，重新载入 31 个寄存器以及 CSR，然后把 sp 重新设置为 sscratch，就完成处理了。

\subsection{中断处理器}
\label{sec:interrupthandler}

这其实就是一个大型 switch。它可以依靠 ksp 读取寄存器的值，而 syscall 的参数就依赖这个实现。完整的 syscall 列表请见 \cref{sec:syscall}，而比较复杂的 syscall 的实现则在和它们相关的章节中有所提及。

为了保证 user-space 进程传来的参数（尤其是指针）是合法的，我会先尝试 VMA-map 参数所在的空间，这在\cref{subsec:pcbinit}中有所描述。如果 VMA 失败了，我选择直接终止程序而不是返回 -EFAULT。对于字符串而言，由于无法预先得知它的结尾，我选择在 strlen 的同时进行 VMA-map。当字符串超出 16MB 的时候，我将会让 syscall 返回 -E2BIG 错误码。

至于 execve 的参数 \cpp{const char *const *argv} 就麻烦得多，不过具体处理方法是类似的。

在 map 完成后，我会将它复制到 kernel-space。同理，我会将 kernel-space 读取的数据复制回去。这是因为 RISC-V 标准\cite{rvPrivManual}建议“只在较短的时间内允许 kernel 访问 user-space 内存”，大概是为了安全考虑。

中断处理器在处理 syscall 的时候，实际上是可以暂停执行并保存上下文的，而且无需手动在每个暂停处维护，只需要一个 \cpp{suspend()} 函数就可以做到。关于它的具体实现，请见\cref{subsec:syscallctx}。
