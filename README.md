# 操作系统内核

这是我的第一个 OS 内核。既然没有经验，看不懂别人的操作系统，只好自己从零搭一个了。或许很多东西并不是最佳实践，但是能跑起来才是最重要的。

这个 OS 完全采用 C++ 实现。

## 启动流程 (RISC-V64)

### 启用虚拟内存

我们规定操作系统的物理内存布局如下，这是由 link.ld 保证的。

```c
.text.low : 0x8020'0000        // 用于启动虚拟内存的一小段代码
pt_root   : 0x8020'1000        // Page Table Root
a0        : 0x8020'2008        // 启动时的 a0，也就是 hart_id
a1        : 0x8020'2010        // 启动时的 a1，也就是 FDT 的地址
.text     : 0x8020'3000        // 操作系统的主体代码
.rodata   : ?
.data     : ?
.bss      : ?
stack_top : .bss + 131072      // 分配 128KB 的栈
kernel_end: stack_top + 4096   // 这之后的一小段会被用于最初的动态内存分配
```

在 link.ld 中可以看见 `.text : AT(LMA_NEXT) {...}` 之类的内容。实际上，`AT` 指定的是将内核加载到的内存地址，也就是 LMA (*load memory address*)。而它们的虚拟地址则是由 `.` 指定的。除了前面的四段以外，之后的 `.text` 等内容都被链接到了高位的虚拟地址，以 `0xffff'ffc` 作为前 26 位。启动时，我们会将 0 - 16GB 的内存映射至虚拟内存，而虚拟地址是物理地址加上 0xffff'ffc0'0000'0000 之后的值。

这个数值实际上是 RISC-V 的规定：虚拟地址需要 sign-extend，而我采取的是 Sv39 页表，所以有 26 位需要置为 1。实际上，这把虚拟地址强行分为了两部分，而普通的 `jalr` 指令是无法隔着这么远跳转的。这就是我选择固定地址，而不是使用类似 `((void (*)()) main_high)()` 之类的原因：链接器无法将过远的地址塞进 `jalr` 里，所以只能用不需要链接的 `jr`。

链接器会把虚拟地址对齐为 8 的倍数，而却不会对 LMA 这么做。为了保证对应关系，我们不能直接认为虚拟地址每次的增加量都是上一段的大小，而最好是直接通过 `AT(. - VIRT_OFFSET)` 之类的方法来确定 LMA。

我将 `_start_high` 固定在了 0x8020'3000。我的方法是给它单独划出一个 `.text.high`，在链接器脚本里把它排在 `.text` 的前面，这样就不需要关注 `.text` 内部的顺序了。

在启动虚拟内存之前，我们还需要临时地将 0x8000'0000 所在的这个 GB 临时映射到它本身，否则下一条指令将会直接触发 instruction page fault。在进入真正的 `.text` 段后，我们将会把它 unmap。

### 启动 interrupt handler

我采用的是 non-vector mode。值得注意的是这个 interrupt handler 的起始地址必须是 4 的倍数，而且保存寄存器的时候用的是 `sd` 而不是 `sw`——这是 64 位。大部分网上的教程都用的是 `sw`。

### 启动内存分配器

我先启动了一个小型的物理内存分配器。它只会占有 4MB 内存：它会用链表将 kernel_end 之后的 4096 个 4KB-frame 连接起来。（或许我应该把这一段也放进 kernel 之中，否则这很不安全。）这相当于一个栈。

接下来，我依靠它启动了一个虚拟内存分配器。我们维护一个 bitmap 来管理虚拟地址空间的最后 1GB，也就是 0xffff'ffff'c000'0000 开始的 1GB 内存。为了让分配尽量均匀（而不是每次都尝试在前几个位置里搜索），我们会记录上一次分配的位置，并从那里开始搜索。一旦找到足够数量的连续空闲空间，就向物理分配器请求对应的页数。为了得知哪些内存是可用的，这需要[读取 FDT](#读取-fdt)。

### 启动 PLIC 和 UART

没什么好说的，照着标准做就可以了。

### 读取 FDT

FDT (*flattened device tree*) 记载着可用的物理设备。它的格式还挺简洁明了的，也非常容易解析。

我的解析依赖动态内存分配：尽管确实没有必要，但写起来更加方便一些，可以直接使用 `os::vector` 之类的容器。这就是我们第一时间启动简单的内存分配器的原因。

我们主要关注的是 initramfs 的位置，以及被保留的内存。同时，这还会探测 virtio 设备。值得注意的是，initramfs 只作测试用，在比赛时加载的是 rootfs。

### 挂载文件系统

我先后挂载了 initramfs 和 devfs。这里的 initramfs 使用的是简单的 CPIO 格式，方便生成和解析。暂时不支持压缩过后的 .cpio.gz。

我的 VFS 采取的是继承与虚函数的形式。比起 C 中显式的函数指针赋值，我更喜欢用 vtable 将它们隐藏起来。由于没有 C++ runtime，我们必须使用 `-fno-rtti`，所以我采取了类似 CRTP 的形式来自动生成类型信息，并仿制 `dynamic_cast`。这和 LLVM 中的用法非常相似。

### 加载 user-space 程序

在 initramfs 中存在一个 ELF `/init`，我写了一个简单的 ELF 解析器将它加载进内存。这里的加载是懒惰的，采用了 VMA。

接下来，将它的 PCB 初始化之后，就可以将它放入 scheduler 了。一切完成后，我才会开启 timer interrupt。至此，操作系统启动完成。
